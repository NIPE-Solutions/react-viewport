# 0.1.0-alpha.0 release readiness

Evidence captured on 2026-09-05 for the Task 12 branch after the final review
correction. Measurements below come from fresh local commands on Node.js 24 and
npm 11. Physical-device results are deliberately excluded because no human
device run has been recorded.

## Architecture summary

The package separates browser measurement from React. A per-window TypeScript
store reads layout, visual viewport, keyboard, safe-area, orientation, and
capability state into one immutable `ViewportState`. A small React layer selects
that store and exposes it through three runtime exports. The distribution ships
ESM, CommonJS, and TypeScript declarations; the documentation is a statically
exported Next.js 16 site.

## Final public API

The exact runtime surface has three named exports: `useViewport`,
`ViewportProvider`, and `useViewportCssVariables`. The exact type surface has
nine named exports: `KeyboardState`, `LayoutViewport`, `SafeAreaInsets`,
`ViewportCssVariablesOptions`, `ViewportOrientation`, `ViewportProviderProps`,
`ViewportState`, `ViewportSupport`, and `VisualViewportState`. The API verifier
confirmed the declaration, ESM, and CommonJS surfaces; no default export or
internal store helper is public.

## Browser API strategy

The active store listens to window `resize` and `scroll`, document `focusin` and
`focusout`, optional VisualViewport `resize` and `scroll`, and optional Virtual
Keyboard `geometrychange`. Every source feeds one animation-frame scheduler, so
state is measured and published atomically instead of exposing event-order
intermediates. Capability flags distinguish native optional APIs from fallback
geometry.

## VisualViewport strategy

When `window.visualViewport` exists, the store reads its width, height, offsets,
page coordinates, and scale. When absent, `visual` mirrors the layout viewport,
uses zero offsets, takes page coordinates from window scrolling, uses scale `1`,
and reports `supported.visualViewport: false`. Dedicated browser scenarios
cover native resize/scroll behavior and the absent-API path.

## Virtual Keyboard strategy

When `navigator.virtualKeyboard` exists, its finite positive `boundingRect` is
authoritative. The store intersects that rectangle with layout bounds and
reports only actual occlusion; empty, invalid, or non-intersecting rectangles
remain closed. Production code never reads or changes `overlaysContent`, so it
does not alter global browser keyboard behavior.

## Keyboard fallback strategy

Without native keyboard geometry, inference requires a keyboard-capable focused
element, a stable keyboard-closed baseline, scale within `0.99` through `1.01`,
and keyboard-sized visual-bottom reduction from that baseline. The baseline is
only an evidence gate. Reported height is always the current clamped occlusion,
`layout.height - (visual.height + visual.offsetTop)`, and that current occlusion
must cross `max(80 CSS px, 15% of layout height)`. Simultaneous layout and visual
shrinkage with zero current occlusion remains closed. Focus alone and
toolbar-sized movement do not open the keyboard. Blur, zoom, and
orientation/baseline changes suppress or reset inference. This conservative
policy intentionally favors false negatives.

## Safe-area implementation

The first subscriber creates one hidden, fixed, zero-sized, non-interactive DOM
probe with padding from all four `env(safe-area-inset-*)` values. Computed pixel
padding is measured into the atomic snapshot; negative, malformed, and
non-finite values normalize to zero. The final unsubscribe removes the exact
probe. Unit coverage verifies fractional values, normalization, reuse, and
idempotent cleanup. Non-zero CSS environment insets generally require
`viewport-fit=cover`; the website exports that Next.js viewport setting and the
README documents it. Physical safe-area behavior remains pending.

## React subscription/store architecture

`useViewport` uses `useSyncExternalStore` with stable snapshot and server
snapshot functions. A `WeakMap` shares exactly one store per `Window`; the first
subscriber installs resources and the last removes listeners, cancels a queued
frame, destroys the safe-area probe, and clears transient baselines.
`ViewportProvider` optionally selects an accessible same-origin window, while a
`null` target deliberately selects the no-op server store. React 18.3 uses the
compatible explicit context `.Provider` form. The packed React 18.3.1 consumer
typechecks, server-renders, hydrates in jsdom, observes a live measurement and
CSS variables, and cleans up; React 19 consumers continue to compile in Vite and
Next.js.

## CSS-variable strategy

`useViewportCssVariables` subscribes directly to the selected store, avoiding a
React rerender solely to write CSS. It owns 14 `--react-viewport-*` properties:
layout and visual sizes, visual offsets and page coordinates, scale, keyboard
height, and four safe-area insets. Unknown pre-measurement dimensions are
removed, zero keyboard/safe-area values remain truthful `0px`, and fractional
lengths are preserved. A per-element, per-property ownership registry gives the
last-mounted live hook deterministic write precedence. Removing either of two
owners reasserts the remaining owner; the final owner restores the latest
consumer value observed before a package write and preserves any later consumer
write. A layout effect on every commit migrates stable refs through initial
null, replacement, and detachment without stale subscriptions or writes.

## SSR/hydration behavior

Imports and server calls do not access browser globals. The stable server
snapshot has `ready: false`, null layout/visual/orientation, closed zero-height
keyboard, zero safe-area values, and false support flags. The hydration browser
suite passed in Chromium, Firefox, and WebKit while failing on any console error
or uncaught page error, and observed neither before nor after the first client
measurement. The genuine packed React 18.3.1 consumer also server-rendered and
hydrated without errors.

## Performance findings

The implementation uses one listener/probe lifecycle per active window, one
queued `requestAnimationFrame` for duplicate source events, and scalar snapshot
comparison to retain object identity and skip unchanged notifications. The
CSS-variable path writes from store notifications without forcing component
rerenders. Browser coverage confirms duplicate-event coalescing into one frame
and no work after final unmount. No synthetic throughput or CPU benchmark was
run for this alpha, so no broader performance claim is made.

## Known browser limitations

Floating and split keyboards may not create detectable bottom occlusion. The
fallback can miss small keyboards and intentionally rejects ordinary browser
chrome movement. Desktop automation cannot reproduce mobile toolbar and
keyboard animation fidelity. Embedded WebViews vary with host configuration.
Safe-area CSS environment values require physical display-cutout verification.
Foldable segments and synthetic keyboard animation are outside v1. Playwright
is pinned to 1.58.2 because newer WebKit revision 2251 failed on this macOS 14
ARM runner before page creation; re-evaluate the pin on a newer runner.
